| 2026-10-25 | Epic 7 admin access: choices beyond the epic | `mockup/admin-login.html` | (1) Our own sessions (table `Session`, only a SHA-256 of the cookie value stored; cookie `__Host-tf_admin` on HTTPS, `tf_admin` on plain http), 30 minutes idle and 12 hours absolute; a half-finished sign-in lasts 10 minutes and is not an admin session. The cookie value changes when the second step completes. (2) The sign-in screen shows one generic message and does not copy two lines of the mockup: "N attempts left" (it would show that an account exists) and "a Super admin has been notified" (there is no notification system; the lockout is in the audit log). (3) Failed password and failed code attempts share one counter; the 5th failure locks the account for 15 minutes (the 6th attempt is refused even with the right password). Attempts for one account are handled one at a time through a database lock, so ten parallel guesses still stop at five. A second limit of 20 sign-in steps per address per 10 minutes is kept in memory (one PM2 process). (4) Authenticator codes are accepted one 30-second step either side and never twice (the last used step is stored); the 8 recovery codes are 75-bit random codes stored as SHA-256 hashes. The authenticator secret is stored encrypted (AES-256-GCM) with `ADMIN_ENCRYPTION_KEY`; without that setting the admin sign-in answers "unavailable" and the public site is unaffected. The key must not be changed once users have enrolled. (5) Passwords: at least 12 characters, at most 72 bytes (bcrypt limit), cost 12; not the email or its name part. (6) A forgotten password is handled by a Super admin: "Reset password" sends a single-use link (48 hours, like an invitation). Using it sets the new password, ends every sign-in of that user and still requires the authenticator code. This was not in the epic; without it nobody could recover an account. There is no self-service "Forgot password" link (the mockup's link was left out). (7) Without a mail server the new user (or reset) link is shown once to the Super admin who created it, so staff can still be invited. (8) The first Super admin is created from the command line: `npm run admin:create -- --email … --name …` (prints the link, writes an audit entry with no actor). (9) US-007.8 (audit log screen, R2) is not built; every event is already recorded. The sidebar shows Leads, Brands & products, Audit log and Settings as dimmed "Soon" entries for the roles that will get them. (10) Admin pages answer 403 through Next's `forbidden()` (experimental flag `authInterrupts`) and are sent with `Cache-Control: no-store`. |
| 2026-10-25 | Epic 9 admin leads: choices beyond the epic | `mockup/admin-leads.html` | (1) The inbox filters are a plain GET form, so every result has a shareable address and works without scripts; the export link uses the same filters. (2) Status, assignee and archive changes are one endpoint; each real change writes its own audit entry with old and new value, and selecting the same value again writes nothing. (3) "Two people change the same lead": the screen sends the status it was looking at; if the lead has moved on the change is refused with 409 and the latest state is shown. (4) Notes are append-only in the database too (a new trigger refuses UPDATE as well as DELETE); the same text from the same person within 30 seconds counts as one note, so a double click or a retry adds one. The note text is not copied into the audit log. (5) CSV: UTF-8 with a byte order mark, read in batches of 500 so large exports stream; cells starting with = + - @ tab or return get a leading apostrophe; the audit entry (who, filters, row count) is written only when the last byte has been produced. (6) Search escapes % and _ (Prisma does not): without it a search for % matched every lead. (7) Retention uses calendar months (29 February clamps to 28 February); the retention screen and its endpoint are Super admin only and nothing is ever deleted. (8) The admin is English-only; Arabic names, companies and messages are shown with `dir="auto"` so they read right-to-left. |
